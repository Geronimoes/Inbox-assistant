  For push-based triggering, there are a few realistic options:

  1. Gmail Pub/Sub push — Gmail's API supports watch() which pushes

  4. Systemd timer/service — A small daemon polling every 60 seconds. More

     Inbox Assistant — Improvement Plan

     Context

     The inbox-assistant is working well after a few days of daily use. Jeroen
     has identified four areas for improvement:
     1. Crontab documentation has drifted from actual schedule
     2. Pipeline efficiency could be reviewed (verdict: already efficient)
     3. Draft responses come too late for emails arriving during the day
     4. Email-derived tasks are transient — they need a persistent home in
     Obsidian

     This plan addresses all four, ordered by dependency and impact.

     Phase 3: Proactive Draft Responses

     Two sub-features: scheduled afternoon triage + on-demand drafts via email
     forwarding.

     3A: Afternoon Triage Runs (--mini flag)

     Problem: Drafts only generated at 06:30. Emails arriving during the day are
      delayed ~24h.

     Solution: Add a --mini flag to fetch_and_triage.py that:
     - Runs the full pipeline (fetch → classify → draft) for new emails only
     (dedup already works)
     - Sends a shorter "Inbox Update" email (no noise section, compact format)
     - Skips overwriting the morning Obsidian daily note
     - Sends a Telegram notification if there are new ACTION/URGENT items

     Cron schedule: Add two weekday afternoon runs:
     0 13 * * 1-5  ... fetch_and_triage.py --mini
     0 17 * * 1-5  ... fetch_and_triage.py --mini

     Files to modify:
     - src/fetch_and_triage.py — add --mini argument; conditionally skip
     Obsidian note; use generate_mini() for briefing
     - src/briefing.py — add generate_mini() and generate_mini_markdown()
     methods (compact HTML/text with just new items)
     - src/notifier.py — add send_update_summary() method for afternoon Telegram
      pings
     - cron/install.sh — add afternoon cron entries
     - CLAUDE.md — document --mini flag

     3B: On-Demand Draft via Email Forwarding

     Problem: Sometimes Jeroen needs a draft NOW for a specific email, without
     waiting for the next scheduled run.

     Solution: A new draft_on_demand.py script that:
     1. Monitors a Gmail label (e.g., _draft-request) for emails forwarded to
     jeroenm+draft@gmail.com
     2. For each found email, extracts the original message and fetches the full
      thread context from Gmail
     3. If the email matches a configured project, also loads recent project
     emails from the Obsidian vault for additional context
     4. Generates a context-aware draft reply using Sonnet
     5. Emails the draft to jeroen.moes@maastrichtuniversity.nl (same as
     briefings) — no Telegram, no Gmail draft
     6. Removes the _draft-request label so the email isn't re-processed

     Gmail setup required: Create a filter: to:jeroenm+draft@gmail.com → apply
     label _draft-request, skip inbox.

     New Gmail method needed: fetch_thread(thread_id) — fetches all messages in
     a thread to provide conversation context to the drafter.

     Thread context for the drafter: The compose_draft() method needs an
     optional thread_context parameter — earlier messages in the thread, so the
     draft can reference prior conversation. For project-matched emails, also
     include recent project vault emails (read from Obsidian markdown files) as
     additional context.

     Cron schedule: Every 2 minutes during work hours (lightweight — just a
     label check when no requests pending):
     */2 8-20 * * 1-5  ... draft_on_demand.py

     Files to create:
     - src/draft_on_demand.py — new script (~120 lines)

     Files to modify:
     - src/gmail_client.py — add fetch_thread(thread_id) method; add
     remove_label(message_id, label) method
     - src/drafter.py — extend compose_draft() to accept optional thread_context
      and project_context parameters, include them in the LLM prompt
     - config.yaml — add draft_on_demand: section (enabled, label, notification
     method)
     - CLAUDE.md — document the feature + Gmail filter setup

     Step 4A: Extend classification prompt

     Add a tasks array to the classification JSON output in prompts/classify.md:

     {
       "email_id": "...",
       ...existing fields...,
       "tasks": [
         {
           "description": "Reply to Margaux about submission deadline",
           "task_type": "explicit",
           "deadline": "2026-03-31",
           "time_estimate_minutes": 10,
           "complexity": "simple",
           "project": "capstone"
         }
       ]
     }

     - task_type: "explicit" (email directly asks for something) vs "implicit"
     (a response/action is expected but not explicitly requested)
     - complexity: "simple" (one-step) vs "complex" (multi-step, generates a
     detail file with steps)
     - project: matches a project id from config, or null
     - time_estimate_minutes: rough estimate for planning
     - Only extracted for URGENT and ACTION emails (not FYI/NOISE)

     ...

     Step 4C: Create src/task_writer.py

     New module (~200 lines) with class TaskWriter:

     - __init__(config) — reads vault_path, loads project list
     - extract_tasks(classifications) — pulls task dicts from classification
     results
     - write_tasks(tasks) — main method:
       a. Read existing TASKS.md (or create from template)
       b. Parse into sections (Urgent / Action Required / Recently Completed)
       c. Check for duplicate tasks (match on description + date within same
     project)
       d. Append new tasks to the correct section, with Obsidian links
       e. For tasks with complexity: "complex", generate and write a detail file
      to Tasks/
       f. For projects with tasks, create/update Tasks/{project_id}.md
       g. Move tasks checked [x] by Jeroen to "Recently Completed" section
       h. Prune completed tasks older than 7 days
       i. Write atomically (.tmp → rename)
     - _generate_complex_breakdown(task, email) — uses Haiku to generate
     step-by-step breakdown for complex tasks (separate cheap LLM call)

     Key safety rules:
     - Never delete or modify existing unchecked task lines — only append new
     ones
     - Detect [x] checkboxes (manual completions by Jeroen) and move them to
     completed
     - Preserve any manual notes Jeroen adds under task items
     - Create Tasks/ directory on first use
