     Feature 2: Project Discovery Tool

     Overview

     A new src/project_discover.py that runs on a weekly schedule (e.g., Sunday
     alongside the style regeneration and dashboard refresh). It analyzes recent
      email, identifies project-like clusters, and emails Jeroen a report with
     suggested projects and instructions for adding them. Can also be run
     manually with --hours for retroactive discovery over longer periods.

     New files

     - src/project_discover.py — main script
     - prompts/project_discover.md — LLM system prompt for clustering

     Config addition

     Add to config.yaml under llm.tasks:
     project_discovery: {provider: anthropic, model: claude-sonnet-4-6}
     Sonnet because clustering/analysis requires reasoning quality (same tier as
      draft_replies).

     How it works

     1. Fetch emails from Gmail — default 2 weeks (--hours 336), configurable up
      to months for retroactive runs
     2. Extract lightweight metadata only: from, to, cc, subject, date, snippet
     (no body text — saves tokens and is sufficient for pattern detection)
     3. Pass existing project configs to the LLM so it excludes already-covered
     topics
     4. LLM identifies clusters by: shared collaborators, recurring subject
     keywords/threads, temporal burst patterns, organizational groupings
     (courses, committees, supervision)
     5. Generate report as both HTML email and Obsidian markdown note
     6. Email the report to Jeroen's UCM address (same briefing.send_to target),
      with:
       - Each suggestion: name, reasoning, email count, date range, sample
     subjects
       - Ready-to-paste YAML config block
       - Brief instructions: "To add any of these, paste the config block into
     config.yaml under projects:, then run python src/project_fetch.py --all 
     --project <id> for the initial backfill"

     CLI interface

     python src/project_discover.py                    # 2-week analysis, sends 
     email report
     python src/project_discover.py --dry-run          # preview report without 
     sending
     python src/project_discover.py --hours 2160       # ~3 months, retroactive 
     discovery
     python src/project_discover.py --hours 4320       # ~6 months (full 
     semester)
     python src/project_discover.py --min-emails 3     # minimum cluster size 
     (default: 3)

     Cron schedule

     0 4 * * 0  cd $SCRIPT_DIR && $PYTHON src/project_discover.py >>
     $LOG_DIR/project-discover.log 2>&1
     Sunday 04:00, after the dashboard refresh (03:00). Weekly cadence is right
     — daily would be noisy, monthly too slow.

     Batching strategy

     - Each email metadata entry ≈ 200-300 bytes. 500 emails ≈ 40K tokens — fits
      in one call.
     - If > 150 emails: split into batches of 100, get per-batch clusters, then
     one merge call.
     - For retroactive runs (months of email, 500 max from Gmail API): single
     call is fine.

     Report output

     Email subject: Inbox Projects — New suggestions (week of Mar 30)

     Email body (HTML, same styling approach as briefing):
     - Section per suggested project with name, reasoning, email count, date
     range
     - Sample subjects from the cluster
     - YAML config block in a code box
     - Instructions for adding + initial backfill command
     - Note at bottom: "These suggestions are based on your email from the last
     2 weeks. To discover older projects, run: python src/project_discover.py 
     --hours 4320"

     Obsidian note: Written to
     {vault_path}/inbox-briefings/project-suggestions/YYYY-MM-DD.md (or a single
      rolling file that gets overwritten weekly — keeps things tidy).

     LLM prompt design (prompts/project_discover.md)

     Key sections:
     - Context about Jeroen's role and typical email patterns
     - Definition of what makes a good "project" (recurring collaboration,
     defined topic, enough volume)
     - Clustering criteria: collaborator groups, subject keywords, thread
     chains, temporal patterns
     - What to exclude: already-configured projects, one-off emails,
     newsletters, system notifications, generic university-wide comms
     - Output: JSON array with name, reasoning, email_count, date_range,
     sample_subjects, suggested_config (id, name, vault_folder, since, keywords,
      collaborators)
     - Conservative approach: only well-defined projects, not vague topic
     clusters

     Script structure (key functions)

     load_config()                          # same pattern as project_fetch.py
     load_existing_projects(config)         # extract configured project
     patterns for exclusion
     prepare_email_metadata(emails)         # strip to
     from/to/cc/subject/date/snippet
     discover_projects(llm, metadata, existing, min_emails)  # LLM call(s) +
     JSON parse
     generate_report_html(suggestions)      # HTML email body
     generate_report_markdown(suggestions)  # Obsidian note
     main()                                 # argparse → fetch → analyze →
     report → send

     Reuses existing patterns from:
     - project_fetch.py — config loading, Gmail auth, argparse structure
     - classifier.py — LLM JSON response parsing with fallback
     - briefing.py — HTML email generation approach
     - gmail_client.send_email() — email delivery

     Files to modify/create
